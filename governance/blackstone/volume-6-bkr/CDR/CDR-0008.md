# CDR-0008 — Add Lightweight Registry Tooling Under BKR

## Problem

`constitution_registry.md` (CDR-0007) tracks constitutional document lineage
as a Markdown table only. As the number of CDRs and registry entries grows,
three gaps appear:

1. CDRs are only discoverable by opening each file individually — there is
   no single index of CDR status, affected volumes, or inter-CDR
   dependencies.
2. The dependency relationships between BKGC, the six downstream volumes,
   and (once drafted) ecosystem constitutions are described in prose in
   `ARCHITECTURAL_FREEZE_NOTICE.md` but are not represented as structured,
   machine-checkable data.
3. `constitution_registry.md` has no machine-readable counterpart, and no
   automated way to check that its own internal claims (unique IDs,
   reciprocal supersession, resolvable CDR references) stay consistent as it
   grows.

`GBC-2-PLAN.md` already anticipates this class of problem (Governance
Linter, Traceability Graph, Automated Compliance Tests) but records explicit
entry criteria for that phase (GB-1 merged to `main`; at least three real PRs
referencing BKGC requirements; tooling design recorded in a CDR) that are
**not yet met**. A full CI-integrated governance pipeline would run ahead of
the project's own documented roadmap.

## Alternatives Considered

1. **Do nothing until GBC-2 entry criteria are met.** Rejected: the
   discoverability and consistency gaps above are already real at the
   current registry size and cost nothing to address with read-only,
   non-invasive additions.
2. **Wire full governance checks into `.github/workflows/ci.yml` now.**
   Rejected: this would (a) treat GBC-2 entry criteria as already satisfied
   when they are not, (b) touch CI configuration outside the governance
   tree, exceeding the scope of a documentation/governance change, and (c)
   make a required build step depend on a still-evolving Markdown/JSON
   registry pair.
3. **Add a new top-level tooling volume or parallel registry tree.**
   Rejected outright: prohibited by `ARCHITECTURAL_FREEZE_NOTICE.md` §5
   without a formal architecture revision.
4. **Add index, dependency graph, JSON mirror, and a standalone (manually
   run, not CI-wired) validation script, entirely under
   `volume-6-bkr/REGISTRIES/` and `volume-6-bkr/CDR/`.** Selected: this is
   "governance tooling that operates on the existing architecture without
   introducing new layers" (`ARCHITECTURAL_FREEZE_NOTICE.md` §4) and a
   direct, minimal instance of the first three `GBC-2-PLAN.md` candidate
   priorities, without prematurely claiming GBC-2 entry criteria are met.

## Decision

Add, entirely within `volume-6-bkr/`:

- `CDR/INDEX.md` — a master index of all CDRs (ID, title, status, amendment
  class, affected volumes, superseded-by, dependencies), generated from the
  existing CDR front matter and bodies.
- `REGISTRIES/governance_dependency_graph.md` — a structured representation
  of the BKGC → BGS → BKC → BRA → BCCM → BKR → BGC dependency hierarchy
  (already normative per `ARCHITECTURAL_FREEZE_NOTICE.md` §2) plus the
  non-hierarchical "derives doctrine from BKGC" relationship for planned
  ecosystem constitutions, so the existing prose relationship is also
  available as data.
- `REGISTRIES/constitution_registry.json` — a machine-readable mirror of
  `constitution_registry.md`, marked as derived/non-authoritative (the
  Markdown file remains the authoritative source; the JSON file must be
  regenerated whenever the Markdown table changes).
- `REGISTRIES/validate_registry.py` — a standalone script (run manually,
  **not** wired into `.github/workflows/ci.yml`) that checks: unique
  Constitution IDs, resolvable supersession references, reciprocal
  supersession pairs, resolvable CDR references, existence of each library
  volume's repository path, and JSON/Markdown mirror consistency.

CI integration of this or any other governance check remains deferred to
GBC-2 and requires its own CDR once GBC-2 entry criteria are satisfied.

## Governing Principles

- `ARCHITECTURAL_FREEZE_NOTICE.md` §3 — governance tooling is explicitly not
  frozen.
- `ARCHITECTURAL_FREEZE_NOTICE.md` §4 — tooling that operates on the
  existing architecture without introducing new layers requires no
  architecture revision.
- `BKR.md` §1.3 — "BKR SHOULD maintain an index mapping each identifier to
  the document and section where it is defined or used."
- `BKR.md` §2.2 — taxonomy/registry additions require a CDR (this one).
- `GBC-2-PLAN.md` — defines the roadmap and entry criteria this decision
  deliberately stays inside of.

## Expected Consequences

- CDRs and constitutional documents remain discoverable and auditable
  without opening every file individually.
- The dependency hierarchy is available as structured data as well as
  prose, without altering the hierarchy itself.
- Internal consistency of the registry (unique IDs, reciprocal supersession,
  resolvable references) can be checked mechanically, on demand, before it
  is ever made a required CI gate.
- No CI configuration, build pipeline, or file outside `governance/` is
  touched by this decision.

## Revisit Conditions

Revisit when GBC-2 entry criteria are met (GB-1 merged to `main`; three or
more real PRs reference BKGC requirements) — at that point, wiring
`validate_registry.py` (or its successor) into CI should be proposed as its
own CDR referencing this one.
