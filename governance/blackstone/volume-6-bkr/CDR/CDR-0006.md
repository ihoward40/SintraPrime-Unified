# CDR-0006 — Govern Advisory Service as a Non-Execution Capability

## Problem

The Advisory Service was introduced in Increment One as a design-only protocol (Protocol v1.0.0). As the project moves toward Increment Two (runtime implementation), there is a risk that the Advisory Service accretes execution authority — dispatching jobs, mutating state, or participating autonomously in agent coordination — which would contradict the architectural boundary established under GB-1.

## Alternatives Considered

1. **Allow the Advisory Service to dispatch or coordinate agents.** Rejected: it would duplicate Hermes's orchestration authority and violate the single-orchestrator principle.
2. **Grant the Advisory Service decision rights over system state.** Rejected: the Principal (Isiah Howard) retains decision authority; advisory output is non-binding by design.
3. **Defer all governance statements until runtime exists.** Rejected: recording the boundary now prevents architecture drift before implementation begins.
4. **Permanently record the Advisory Service as a governed, non-execution capability with deferred runtime.** Selected: it establishes a stable reference for Increment Two implementers without blocking planning.

## Decision

The Advisory Service is a **governed capability** with the following fixed architectural properties:

- **No execution authority.** The Advisory Service never approves, dispatches, or mutates system state. It produces advisory output only.
- **Hermes remains the orchestration authority.** All transport, mission routing, and agent coordination remain the responsibility of Hermes.
- **The Principal remains the decision authority.** Advisory output is non-binding; the Principal decides.
- **Runtime implementation is intentionally deferred beyond Protocol v1.0.0.** Increment Two MAY plan, but is NOT yet authorized to implement, runtime components.
- **Increment Two planning scope is bounded** to: Hermes command registration, Context Manifest assembly, Provider interface, Slack formatter, and Audit record generation. Nothing beyond these items is authorized without a separate implementation review.

## Governing Principles

- GB-1 § Architectural Freeze — improvements occur within existing architectural boundaries before proposing new layers or restructuring the library.
- Single orchestrator: Hermes orchestrates; the Advisory Service advises.
- Advisory classification: Advisory Only; Authority: None; Decision Rights: None.
- CDRs are immutable; corrections require a new CDR.

## Expected Consequences

- Increment Two implementers have a stable architectural reference before any code is written.
- Architecture drift (e.g., an additional governance volume, a parallel registry, or autonomous advisory behavior) is detectable against this record.
- The layered architecture and disciplined progression established under GB-1 is preserved.

## Revisit Conditions

Revisit if operational evidence demonstrates that the non-execution boundary itself requires revision, or if Increment Two implementation reveals that the bounded planning scope is insufficient. Any change to execution authority MUST pass through the formal GB-1 amendment process rather than isolated implementation.
