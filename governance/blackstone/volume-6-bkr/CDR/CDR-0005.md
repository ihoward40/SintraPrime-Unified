# CDR-0005 — Adopt Requirement Traceability System

## Problem

As the library grows, it becomes difficult to verify that downstream standards, engines, and tests actually implement constitutional requirements.

## Alternatives Considered

1. **Manual review for every change.** Rejected because it does not scale.
2. **Permanent requirement identifiers with upstream traces.** Selected because it enables automated audits and end-to-end traceability.

## Decision

Every mandatory rule receives a permanent identifier:

- `BKGC-R-xxx` for constitutional requirements
- `BGS-S-xxx` for standards
- `BKC-C-xxx` for concepts
- `BRA-E-xxx` for engines and API requirements
- `BCCM-T-xxx` for tests
- `BKR-TERM-xxx` for registry terms
- `BGC-CASE-xxx` for cases
- `CDR-xxxx` for decision records

Every downstream identifier MUST trace to at least one upstream identifier. BCCM tests can directly assert coverage of BKGC requirements.

## Governing Principles

- BKGC § 2.3 Auditability
- BKGC § 18.1 Decision Traceability

## Expected Consequences

- Gaps between requirements and tests are detectable.
- Terminology drift is auditable.
- Certification reports can cite exact requirements satisfied.

## Revisit Conditions

Revisit if the identifier scheme proves insufficient for cross-references between volumes or if automated validation requires additional metadata.
